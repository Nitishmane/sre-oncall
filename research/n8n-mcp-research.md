## Part A: Three n8n MCP Integration Modes

These three are frequently confused because they all have "n8n" and "MCP" in their names. They do fundamentally different things and move data in different directions.

---

### Mode 1: n8n MCP Server Trigger (n8n → exposes tools TO an external agent)

**What it is:** A native n8n node that turns an n8n workflow into an MCP server. Your external AI agent (in our case, the SRE-Oncall agent on the TrueForge harness) connects to it and calls the tools it exposes. The n8n side defines the tool names, descriptions, and schemas; the AI side calls them.

**Direction:** External AI agent → calls → n8n workflow tools

**Transport:**
- Supports both SSE (Server-Sent Events) and Streamable HTTP
- SSE is now deprecated; Streamable HTTP is the recommended transport for new implementations
- stdio is NOT supported — this is webhook-based, not process-based
- For reverse proxies (nginx/Caddy), proxy buffering must be disabled for the `/mcp/` path

**Endpoint URL shape:** Auto-generated by n8n; two URLs are produced:
- Test URL: active during workflow development
- Production URL: active after workflow is published/activated

**Auth:** Bearer token authentication or Header authentication (HTTP request credentials in n8n)

**Self-hosted vs Cloud:** Works on both. Self-hosted Docker is free (community edition). n8n Cloud starts at €20/month (Starter, 2,500 executions).

**Queue mode caveat:** In multi-replica webhook deployments, all `/mcp*` requests must be routed to a single dedicated webhook replica. SSE/Streamable HTTP require persistent connections to the same server instance — important for any production k8s/horizontal-scaling setup.

**Setup steps (self-hosted):**
1. Add an MCP Server Trigger node as the workflow entry point
2. Connect Custom n8n Workflow Tool nodes to define each capability
3. Write clear tool names and descriptions (treat them like typed function signatures — vague descriptions cause wrong or no tool calls)
4. Activate the workflow to generate the production URL
5. Configure your SRE agent's MCP client config with the SSE/Streamable HTTP URL and bearer token

**Source:** [n8n MCP Server Trigger docs](https://docs.n8n.io/integrations/builtin/core-nodes/n8n-nodes-langchain.mcptrigger), [n8n MCP in 2026: Three Ways to Connect](https://www.upendrasengar.com/blog/n8n-mcp-in-2026-three-ways-to-connect)

---

### Mode 2: n8n MCP Client Tool Node (n8n agent → calls an external MCP server)

**What it is:** A native n8n sub-node that lets an AI agent running inside n8n call tools from an external MCP server. This is the reverse of Mode 1. Less relevant for the SRE-Oncall stack (where the agent lives outside n8n on TrueForge), but worth knowing for hybrid designs.

**Direction:** n8n AI agent → calls → external MCP server tools

**Transport:** SSE endpoint (the docs page still references SSE; Streamable HTTP support is noted in the broader n8n MCP Client node)

**Auth:** Bearer, generic header, multiple headers, OAuth2, or none

**Configuration:** Supply the SSE endpoint URL of the target MCP server and select which tools to expose to the agent (all, specific subset, or exclusion list)

**When you'd use it:** If n8n is the orchestrator and your SRE-Oncall agent is an n8n AI Agent workflow that needs to call the TrueForge harness tools (Grafana MCP, ArgoCD MCP, etc.) as external MCP servers.

**Source:** [MCP Client Tool node docs](https://docs.n8n.io/integrations/builtin/cluster-nodes/sub-nodes/n8n-nodes-langchain.toolmcp), [MCP Client node docs](https://docs.n8n.io/integrations/builtin/core-nodes/n8n-nodes-langchain.mcpclient)

---

### Mode 3: czlonkowski/n8n-mcp — AI Agent Builds and Manages n8n Workflows (the "builder" mode)

**What it is:** A community-built MCP server (22.8k GitHub stars, MIT licensed, actively maintained) that wraps n8n's REST API and node documentation into MCP tools, letting an AI agent CREATE, EDIT, ACTIVATE, and RUN n8n workflows through conversation. This is the "agent-built automation" pattern.

**Direction:** External AI agent → creates/manages → n8n workflows

**Repository:** [czlonkowski/n8n-mcp](https://github.com/czlonkowski/n8n-mcp)

**What it exposes (two tool categories):**

*Documentation tools (7 tools, no n8n API key needed):*
- `search_nodes` — full-text search across 2,541 nodes (832 core + 1,709 community)
- `get_node` — node info, docs, property search
- `validate_node` / `validate_workflow` — validation before deployment
- `search_templates` / `get_template` — 2,352 workflow templates
- `tools_documentation` — self-documentation

*n8n Management tools (16 tools, n8n API key required):*
- Full workflow CRUD (create, read, update, delete)
- Workflow activation/deactivation via API
- Execution management and logs
- Version control and rollback
- Credential management
- Security auditing
- Folder management

**Transport:** HTTP Streamable (MCP over HTTP, not stdio) when running as a server

**Auth:**
- Connecting to the MCP server: `MCP_AUTH_TOKEN` (bearer token, minimum 32 chars)
- Connecting to n8n: `N8N_API_KEY` from n8n Settings → API (non-Enterprise keys have full scope; Enterprise keys can be scoped to minimum permissions)

**Docker deployment (key env vars):**
```
N8N_MODE=true
MCP_MODE=http
N8N_API_URL=http://n8n:5678        # or http://localhost:5678
N8N_API_KEY=<from n8n Settings → API>
MCP_AUTH_TOKEN=<openssl rand -hex 32>
AUTH_TOKEN=<must match MCP_AUTH_TOKEN exactly>
PORT=3000                           # default
```
The MCP endpoint served is at `http://localhost:3000/mcp`.

**Workflow activation via API:** Fully supported. The n8n REST API (`POST /api/v1/workflows/{id}/activate`) activates workflows programmatically. The n8n-mcp management tools wrap this.

**Gotcha — "prototyping" label:** Some sources describe this as not production-ready at scale due to potential n8n API changes between releases. However, with 22.8k stars and the hosted tier (dashboard.n8n-mcp.com, 100 free tool calls/day), it is mature enough for a hackathon demo and increasingly production-used. The core risk is that n8n's internal workflow JSON schema can change between major versions, which can break AI-generated workflow payloads.

**Source:** [czlonkowski/n8n-mcp README](https://github.com/czlonkowski/n8n-mcp/blob/main/README.md), [n8n-mcp deployment docs](https://github.com/czlonkowski/n8n-mcp/blob/main/docs/N8N_DEPLOYMENT.md), [PulseMCP entry](https://www.pulsemcp.com/servers/czlonkowski-n8n)

## Part B: Hosting and ngrok Analysis

### n8n Self-Hosted (Docker, Community Edition)
- **Cost:** Free software. Only pay for compute. 4 GB RAM / 2 CPU is the recommended minimum (~$40–80/month on cloud VMs; $0 locally for a hackathon).
- **License:** Fair Code (Sustainable Use License for enterprise features; free for self-hosted community use)
- **Executions:** Unlimited locally
- **Docker quick start:**
  ```bash
  docker run -it --rm \
    -p 5678:5678 \
    -v ~/.n8n:/home/node/.n8n \
    n8nio/n8n
  ```

### n8n Cloud (2026 pricing)
- Starter: €20/month (2,500 executions, 5 concurrent) — free trial available, no card required
- Pro: €50/month (10,000 executions, 20 concurrent) — free trial available
- Business: €667/month (40,000 executions) — 14-day trial, card required
- No permanent free tier as of 2026

**For the hackathon: self-hosted Docker locally is the correct choice.** Zero cost, full control, no execution limits.

### What Needs ngrok and Why

| Scenario | ngrok Needed? | Why |
|---|---|---|
| SRE-Oncall agent (on same machine) calling n8n MCP Server Trigger | No | Agent calls `localhost:5678/mcp/...` directly |
| SRE-Oncall agent calling n8n-mcp builder server (Mode 3) | No | `http://localhost:3000/mcp` directly |
| PagerDuty webhook firing INTO n8n (inbound from SaaS) | YES | PagerDuty is external and needs a public URL to POST to |
| Slack slash command / action firing INTO n8n | YES | Slack's servers POST to your webhook URL |
| External SaaS (Grafana alerting, GitHub webhooks) firing INTO n8n | YES | Any external SaaS calling in requires public reachability |
| n8n calling OUT to PagerDuty/Slack/GitHub APIs | No | Outbound from n8n works with no tunnel |

**ngrok setup for n8n:** Expose port 5678 (the n8n editor + webhook port). Set two n8n env vars:
```
N8N_HOST=your-subdomain.ngrok-free.app
WEBHOOK_URL=https://your-subdomain.ngrok-free.app/
```

**MCP-specific ngrok note:** The MCP Server Trigger node's SSE/Streamable HTTP endpoint lives under `/mcp/` on the same port 5678. If the TrueForge harness agent is local and calls localhost, no ngrok needed. If a cloud-hosted agent needs to reach the MCP Server Trigger, that endpoint also goes through ngrok via the same tunnel — no separate exposure needed.

**Free ngrok caveat:** (See editorial note at top — the free tier's one claimable static domain covers this; Cloudflare Tunnel is the fallback.) NOTE: ngrok free allows **1 concurrent tunnel** — PagerDuty→orchestrator (port 8080) and SaaS→n8n (port 5678) can't both have tunnels on free tier. Options: route n8n inbound webhooks through the orchestrator (path-based forwarding), use Cloudflare Tunnel for the second endpoint, or skip inbound-to-n8n entirely (agent invokes n8n tools directly; PD webhooks land only on the orchestrator). Default: single tunnel to the orchestrator; no direct SaaS→n8n inbound needed for the demo.

**Sources:** [ngrok n8n docs](https://ngrok.com/docs/universal-gateway/examples/n8n), [northflank n8n hosting guide](https://northflank.com/blog/how-to-self-host-n8n-setup-architecture-and-pricing-guide), [n8n pricing](https://n8n.io/pricing/)

## Part C: SRE-Relevant Use Cases, Ranked by Demo Value

### Tier 1 — High Demo Impact, Low Setup Effort

**1. Multi-Channel Incident Notification (Slack + SMS/call via Twilio)**
- Demo value: Immediate visual proof — audience sees Slack message AND phone buzzes simultaneously
- n8n template: [Call & SMS Twilio MCP Server](https://n8n.io/workflows/5078-call-and-sms-twilio-tool-mcp-server/) exposes `make_call` and `send_sms` as MCP tools; the SRE agent calls them directly
- Effort: Low — template exists, wire up Twilio creds and Slack creds
- SRE relevance: Core on-call notification path

**2. PagerDuty → Jira + Slack + Google Sheets Incident Lifecycle**
- Demo value: Shows full incident lifecycle automated in one workflow
- n8n template: [Automate Incident Management with PagerDuty, Port AI, Jira & Slack](https://n8n.io/workflows/11610-automate-incident-management-with-pagerduty-port-ai-jira-and-slack/) — triggers on PagerDuty webhook, queries service context, AI-assesses severity, creates Jira ticket with checklist, notifies Slack, on resolve calculates MTTR and AI-generates postmortem template, schedules postmortem meeting
- Effort: Medium — requires PagerDuty, Jira, and Port credentials; but template does the heavy lifting
- SRE relevance: This is the money demo — full incident-to-postmortem automation

**3. Agent-Built Workflow Demo (the "killer pattern")**
- Demo value: The audible "wow" moment — user asks the agent in chat to "send a P1 SMS to the EM on-call whenever a PagerDuty critical fires" and the agent creates and activates an n8n workflow in real time
- n8n-mcp tools used: `search_nodes` (find Twilio + PagerDuty nodes), `get_template` (find a base to start from), `validate_workflow`, then management tools to `POST /workflows` and `POST /workflows/{id}/activate`
- Effort: Medium — requires n8n-mcp running, good system prompt describing node schemas, and a dev-instance n8n to build into
- SRE relevance: Proves the agent can self-extend its automation capabilities — closes the loop on the hackathon narrative

### Tier 2 — Good Demo Value, Moderate Setup

**4. Escalation Chain Automation**
- When a P1 stays unacknowledged for N minutes, n8n (triggered by a scheduled/cron check) escalates: first Slack DM to on-call, then Slack to manager, then Twilio call to director
- Effort: Medium — build a cron-triggered workflow polling PagerDuty via n8n's PagerDuty node
- Template base: [Incident response workflow parts 2 & 3](https://n8n.io/workflows/354-incident-response-workflow-part-2/)

**5. Scheduled Overnight Incident Summary → Slack**
- "Every morning at 8am, post a summary of overnight PagerDuty incidents to #sre-daily"
- This is exactly the kind of NL request the SRE agent should turn into an agent-built n8n workflow (Mode 3)
- Effort: Low once n8n-mcp is running — agent does the work
- Demo narrative: "Watch the agent create its own automation from a plain English request"

**6. Stakeholder Status Page Updates**
- On P1 trigger → n8n posts a status update to Statuspage.io (or a Slack #status channel) using the HTTP Request node; updates again on resolve with MTTR
- Effort: Low-Medium — n8n has Statuspage.io node; or use HTTP Request to any status API
- SRE relevance: Keeps non-technical stakeholders informed automatically

### Tier 3 — Solid but Less Visually Dramatic

**7. Auto-Create GitHub/Linear Issue from Incident**
- PagerDuty incident → n8n → GitHub Issue or Linear ticket with enriched context (service owner, recent deploys, runbook link)
- n8n has native GitHub and Linear integrations
- Effort: Low-Medium

**8. Incident Enrichment (Customer Impact Lookup)**
- On alert trigger, query a customer DB or analytics API for affected customer count, pipe that context back into the PagerDuty incident notes and Slack alert
- Effort: Medium — requires HTTP Request node to internal APIs

**9. Postmortem Distribution**
- After incident resolution, n8n generates a postmortem doc (Google Doc or Notion page), schedules a calendar invite, and emails stakeholders
- n8n has Google Calendar, Google Docs, and Notion nodes
- Effort: Medium

**10. Scheduled Synthetic Health Checks**
- n8n cron workflow pings key service endpoints every 5 minutes; if any fail, creates a PagerDuty incident via PagerDuty API
- n8n template: [Monitor scheduled workflow health](https://n8n.io/workflows/13290-monitor-scheduled-workflow-health-in-n8n-with-automatic-trigger-checks/)
- Effort: Low

**Sources:** [n8n incident templates](https://n8n.io/workflows/9826-automate-incident-response-with-jira-slack-google-sheets-and-drive/), [PagerDuty/Jira/Slack template](https://n8n.io/workflows/11610-automate-incident-management-with-pagerduty-port-ai-jira-and-slack/), [Twilio MCP server template](https://n8n.io/workflows/5078-call-and-sms-twilio-tool-mcp-server/)

## Part D: Recommended Integration for the SRE-Oncall Stack

**Use Modes 1 and 3 together. Do not bother with Mode 2 (n8n as MCP client) for this stack.**

### Primary integration: Mode 3 (n8n-mcp builder) as an MCP tool in TrueForge

The SRE-Oncall agent gets `n8n-mcp` as one of its MCP servers alongside Grafana, Kubernetes, ArgoCD, etc. When a user says "set up a workflow to..." the agent delegates to n8n-mcp to build and activate it.

**Config to add to TrueForge agent MCP settings:**
```json
{
  "mcpServers": {
    "n8n-workflow-builder": {
      "url": "http://localhost:3000/mcp",
      "transport": "http",
      "headers": {
        "Authorization": "Bearer <MCP_AUTH_TOKEN>"
      }
    }
  }
}
```

**Required env vars for n8n-mcp container:**
```
N8N_MODE=true
MCP_MODE=http
N8N_API_URL=http://localhost:5678
N8N_API_KEY=<generated from n8n Settings → API → Create API Key>
MCP_AUTH_TOKEN=<openssl rand -hex 32>
AUTH_TOKEN=<same value>
PORT=3000
```

### Secondary integration: Mode 1 (MCP Server Trigger) for standing SRE capabilities

Pre-build 2-3 n8n workflows that the SRE agent can invoke as stable tools:
- "notify-oncall" — Slack + Twilio SMS/call for a given incident
- "create-incident-ticket" — PagerDuty event → Jira issue + Slack thread + Google Sheets row
- "escalate-incident" — multi-step escalation chain with time delays

These are exposed via the MCP Server Trigger node and registered with the TrueForge agent as permanent MCP tools (stable production URLs, bearer token auth).

**Human approval gate:** For write actions (sending SMS, creating tickets, activating new workflows), the TrueForge harness approval gate already handles this — no changes needed on the n8n side. n8n executes what the approved agent calls; the gate lives at the harness layer.

**ngrok for the hackathon:** Single tunnel to the orchestrator (static domain). The TrueForge agent calls all n8n MCP endpoints on localhost — no tunnel. No direct SaaS→n8n inbound is needed for the demo (see Part B note).

## Part E: Gotchas and Risks

**1. MCP Server Trigger persistence (queue mode)** — multi-replica n8n breaks SSE/Streamable HTTP; irrelevant for single local Docker instance.

**2. n8n-mcp workflow JSON schema drift** — n8n's internal workflow format can change between major versions; AI-generated payloads may become invalid. Mitigation: pin the n8n Docker image version and update n8n-mcp in lockstep. Always `validate_workflow` before activating.

**3. Tool description quality is critical for Mode 1** — MCP Server Trigger routing relies entirely on the natural-language tool descriptions. Write them like typed function docstrings: what it does, required inputs, returns, when to use vs alternatives.

**4. ngrok URL stability** — use the free static domain (see editorial note) or Cloudflare Tunnel; free tier allows only 1 concurrent tunnel (see Part B).

**5. n8n API key scope on non-Enterprise** — the key n8n-mcp uses is full-access (same permissions as admin). Fine for hackathon; a real credential risk in production (Enterprise adds scoped keys).

**6. Tool sprawl and latency** — too many exposed MCP tools raises token cost and degrades decisions. Keep standing Mode 1 tools focused (3–5 max); builder tools are used only when explicitly constructing automation.

**7. n8n-mcp hosted tier limit** — dashboard.n8n-mcp.com caps at 100 tool calls/day. Self-host the Docker image for the hackathon.

**8. n8n Cloud execution limits** — a busy incident can burn 10–20 executions; self-hosted avoids the cap entirely.
