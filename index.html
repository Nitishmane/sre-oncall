SRE-Oncall

An AI on-call engineer that wakes up when a Grafana alert fires. It debugs the incident autonomously — reading live Kubernetes events, Prometheus metrics, and ArgoCD deploy history — then proposes a healing action behind a human approval gate, opens a Qodo-reviewed PR, watches the metric recover until the alert resolves itself, and writes the postmortem. Built on the open-source TrueForge agent harness.

Architecture

The whole detect→heal loop is local: a fault trips a Grafana alert rule, the alert webhooks straight into the orchestrator, and the agent heals it — no SaaS round-trip, no tunnel. Vercel serves the human surfaces; the authenticated ngrok bridge exists only for the chatbox.

How an incident flows

  1. Alert fires. A fault in the demo service pushes a metric over its threshold; the Grafana alert rule evaluates to firing.demo service → Prometheus → Grafana
  2. Grafana webhooks the orchestrator. The webhook contact point POSTs to localhost:8080 — a local-to-local hop, bearer-token verified before anything else happens.Grafana → local orchestrator
  3. The healing session starts. The orchestrator starts a TrueForge session with one framed instruction: “Heal Grafana alert: rule <UID>, fingerprint <FP>” — never the raw alert labels (prompt-injection defense); the agent fetches details itself.orchestrator → TrueForge
  4. Parallel investigation. Subagents pull the alert's evaluation data, metrics and logs (Grafana MCP), live pod events and crash logs (Kubernetes MCP), and recent deploys (ArgoCD MCP): “started 4 minutes after sync #42.”agent → MCP tools
  5. Root cause + proposal. The matching SKILL.md runbook guides the diagnosis; the agent drafts a fix — a manifest change, an ArgoCD rollback, or a Terraform change with the plan output attached.agent
  6. ⏸ Approval gate. The session pauses. Approve/Reject buttons appear in Slack and the chatbox. Nothing is written anywhere until a human clicks Approve.agent → human
  7. Fix ships, system heals. The agent opens the PR, Qodo reviews it, the human merges; the agent watches the metric drop back under the threshold and the Grafana alert auto-resolves.agent → GitHub / cluster
  8. Paper trail. Grafana's resolved notification triggers a postmortem session that fills a page in the Notion Postmortems database — timeline, root cause, MTTR, follow-ups — and posts the summary + link to Slack; at shift change, a handoff summary covers what the next oncall inherits.agent → Notion / Slack

The healing loops

Every loop opens with a signal, closes with the same signal recovering, and pauses at an approval gate before anything is written. Six loops, one agent.

01Metric healing loop — the core
Trigger: Grafana alert rule fires on a Prometheus metric (HighErrorRate, HighLatencyP99, OOMKilled, RestartsSpiking, PodPending)
fault→metric crosses threshold→Grafana → webhook→ healing session→investigate: metrics · logs · pod events→ ⏸ approve fix→PR merged (Qodo-reviewed)→ metric recovers → alert auto-resolves
02Event healing loop
Trigger: Kubernetes event pattern in Loki (FailedScheduling, ImagePullBackOff, evictions) — failures that never show up as a metric. Events flow k8s → Alloy → Loki; a Grafana rule alerts on the Loki query.
k8s event→Alloy → Loki→Grafana Loki-query alert→ same webhook→healing session→ ⏸ approve fix→event stream goes quiet → resolves
03Deploy-regression loop
Trigger: an alert that correlates with a recent ArgoCD sync — “this started 4 minutes after sync #42.”
alert→ArgoCD MCP: sync history→regression identified→ ⏸ approve rollback→ArgoCD rollback→ recovery→follow-up fix PR for the bad change
04Infra-as-code loop
Trigger: root cause sits in infrastructure config (limits, quotas, provisioning) rather than app code.
root cause in HCL→Terraform MCP: author fix→ PR with terraform plan attached→ ⏸ approve→apply→recovery
05Escalation loop
Trigger: healing is blocked — approval times out, fix fails, or the alert re-fires. The agent never retries destructive actions unattended; it escalates to humans instead.
healing blocked→n8n escalate-incident workflow→ Slack DM oncall→manager→SMS / call→ human engages, agent assists
06Learning loop
Trigger: every resolution — and every plain-English automation request in the chat.
resolved→Notion postmortem: timeline · root cause · MTTR · follow-ups→ handoff summary at shift change→ ⏸ approve→agent builds new n8n automations — the system extends itself

Safety model

Authenticated chatboxThe Vercel chat UI can start harness sessions, so it sits behind a sign-in whose account list fails closed — passwords stored only as scrypt verifiers. Harness calls are proxied server-side; the browser never sees the tunnel URL or token.
Human approval gatesEvery write — Grafana silences/annotations, k8s mutations, ArgoCD rollbacks, PR merges, n8n workflow activation — pauses the session until a human approves.
Authenticated ingress onlyGrafana webhook posts carry a bearer token (optional HMAC); the chat bridge requires its own bearer. Raw TrueForge is never exposed to the internet.
Injection trust boundaryOnly the alert rule UID and fingerprint enter the prompt. Alert labels, annotations, and author-controlled text never do.
Read-only by defaultThe agent's MCP toolset is read-only; write tools are explicitly enabled and always gated.

Live demo topology — what runs where

Vercel serves the face. The local host runs the brain — including the whole alert→heal loop. The only tunnel is the authenticated chatbox bridge.

  • Slack bot Socket Mode = persistent WebSocket

☁ Cloud SaaS
  • GitHub repo · PRs · hosted MCP · Qodo app
  • Notion Postmortems database — pages created via integration token
  • Slack workspace
  • Anthropic API the model behind the harness
The ngrok bridge: one static domain (https://<name>.ngrok-free.app) forwards to the orchestrator's /chat proxy — bearer-token required, raw TrueForge never exposed. It carries exactly one flow: the Vercel chatbox's API + SSE traffic. Alert ingress is local-to-local (Grafana → orchestrator) and everything else the agent does is outbound — no tunnel.

Deploying to Vercel

The static page needs nothing but the repo. Preferred setup: connect the GitHub repo in the Vercel dashboard — every PR then gets a preview deployment alongside its Qodo review.

# one-time
npm i -g vercel && vercel login

# deploy this page (static, zero config)
vercel --prod

# later: the chatbox app — server-side env vars only (never NEXT_PUBLIC_)
AUTH_SECRET=…                # Auth.js sessions
CONSOLE_USERS=alice:scrypt$… # accounts allowed to chat; empty means nobody
TRUEFORGE_API_URL=https://<your-static-domain>.ngrok-free.app
TRUEFORGE_BRIDGE_TOKEN=…     # bearer the orchestrator /chat proxy requires

This page is static and needs no secrets. The chatbox project holds only its own auth/bridge secrets, server-side. All vendor credentials (Grafana, GitHub MCP, Slack, Anthropic, n8n) stay on the local host.
